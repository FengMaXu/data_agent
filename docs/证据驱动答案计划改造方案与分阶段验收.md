# 证据驱动答案计划改造方案与分阶段验收

状态：待评审，未授权实施或默认推广。
修订：纳入离线选择、轮次预算、反证优先与渐进迁移四项审阅意见。本次仅完善方案，不代表代码实现或验收完成。

## 1. 目标、非目标与原则

### 1.1 目标

1. 模型不能自行把推断升级为用户确认或权威事实。
2. 证据资格、语义支持、解释采用三者独立，避免“有引用即正确”。
3. 重要口径选择可追溯到证据、核查记录或明确的临时解释。
4. candidate 被采用时，无论是否出现 anomaly，都自动随结果披露。
5. 版本、hash、Artifact 与 Receipt 继续由 Runtime 维护，减少模型手工协议负担。
6. 七槽位与 SQL 能核对到哪里，就报告到哪里；不支持不能伪装成通过。
7. 相同预算下验证准确率、完整性、披露质量与成本，再决定推广。

### 1.2 非目标

- 不引入默认多 Agent 辩论或通用 SQL 正确性证明。
- 不一次性建设覆盖任意 SQL 的 DSL 或编译器。
- 不修改 KTX 的语义查询协议。
- 不把置信度分数当作提升证据等级的条件。
- 不把历史 Gold、Gold CSV 或由 Gold 反推的口径注入在线证据。
- 不将所有未决解释升级为硬阻断。

### 1.3 沿用的约束

ADR-0003 为默认动作依据：检测告知而非裁决；身份完整性及有权威合同支撑的确定性形状违规可硬阻断。交互澄清与其他严格交付策略必须显式配置。继续保持 exploration 不可发布、候选不可变、旧 Spec 候选失效及精确 Receipt 交付。

## 2. 总体结构

```text
用户问题 / 澄清 / 文档 / Schema / exploration Artifact
                         ↓
                    Evidence Store
                         ↓
模型 propose_plan → Answer Session → 不可变 Plan Revision
                         ↓
                  Risk / Check Planner
                         ↓
                执行候选 + 有界核查
                         ↓
         Candidate + Coverage + Verification Records
                         ↓
                 Delivery Policy
                         ↓
            数据 + Disclosure + Receipt
```

外部 Interface 隐藏版本 hash、发布登记等协议细节；内部仍复用 Spec Authority、Query Assurance、Query Digest、Anomaly Registry 和 Publication Registry。不要为每个名词新增一层仅透传的模块。

## 3. 数据模型与所有权

### 3.1 Evidence：只由 Runtime 登记证据身份

建议最小字段：

```text
evidenceId, taskId, sourceKind, sourceIdentity, sourceRevision,
locator, contentHash, authority, observedAt, payloadRef
```

- sourceKind 至少区分 request、clarification、business_document、schema、query_observation。
- 文档修订与查询 Artifact 身份必须可解析；不得记录密钥或无关敏感行。
- 用户确认只能来自 Host 实际收到的回答事件，模型不能构造该事件。
- request quote 精确匹配只证明出处真实，不证明对题面含义的推导正确。
- query_observation 不能仅因样本支持而成为业务定义。
- 恢复任务时证据登记必须恢复；跨任务引用默认拒绝，共享文档通过受控导入产生任务引用。

### 3.2 Plan：唯一的答案解释来源

保留七槽位作为展示及兼容投影，初期沿用 Answer Spec 存储和版本链，不另建互相竞争的真相源。

```text
PlanRevision:
  taskId, revisionId, parentRevisionId, contentHash
  sevenFacets
  claims[]
  decisions[]
  calculation?        # 逐步支持的结构化计算
```

Claim：一个可被核查的语义主张。

```text
claimId, statement, facetPaths[], proposedEvidenceRefs[], materiality
```

Decision：本次采用的解释，独立于证据是否充分。

```text
decisionId, facetPaths[], alternatives[], selectedAlternativeId?,
selectionBasis: evidence | user_choice | provisional_literal,
selectionPolicyVersion?, selectionReason?, selectionInputHash?,
state: selected | pending_clarification
```

- 对已识别为互斥的 alternatives，只能选一个；未决时允许不选。
- 不强制每个请求生成多项假设，不为无歧义问题制造候选。
- alternative 未采用不等于被事实反驳。
- 模型可提出 materiality，Runtime 对已知高风险结构补充标记；不能假定能自动发现所有隐藏歧义。
- 不再把槽位 status 当作独立权威源，兼容 facetStatus 由受支持证据和未决项投影生成。

### 3.3 Verification：核查不是模型自由修改的状态

```text
verificationId, claimId, revisionId, candidateId?, evidenceRefs[],
method, methodVersion,
result: supported | refuted | inconclusive | unavailable | not_applicable,
scopeOfSupport, limitations
```

method 区分 user_confirmation、formal_rule、probe、semantic_assessment 等。语义审查的 supported 不自动授权 Hard Constraint。状态由登记事件及合格核查结果归约，模型只提交主张和证据引用。

明确区分三个维度：

1. 证据身份是否有效。
2. 证据是否支持主张，以及支持范围。
3. 本次是否采用该解释。

Hard Constraint 继续单独按 Evidence Authority 与规则适用性建立；不得用“supported”这一统一标签直接替代资格判断。

### 3.4 Delivery：数据与披露是一个交付对象

```text
DeliveryEnvelope:
  candidateId, revisionId, artifactId
  selectedDecisions[]
  unresolvedAdoptedClaims[]
  checkCoverage[], limitations[]
  disclosureVersion, disclosureHash
  receipt
```

JSON 审计字段保留精确关联，用户视图使用简短口径说明。CSV 使用受控 sidecar/附件与同一 Receipt 绑定；内联使用结果卡片。审计日志中存在披露不等于用户已经看到披露。

## 4. 模型与 Runtime 的 Interface

概念性 Interface，不要求一次性重命名现有工具：

```text
propose_plan(baseRevisionId, planProposal) → revisionId + openIssues
explore(sql) → evidenceId + internalPreview
evaluate_candidate(revisionId, sql, selectedDecisionIds) → candidateId + checks
deliver(candidateId) → result + disclosure + receipt
```

- revisionId 是不透明句柄，模型不再复制 hash；Runtime 从句柄解析并校验不可变身份。
- 必须明确绑定 revisionId，禁止并行执行时暗中使用“最新版本”。
- 旧版本候选只能作为内部证据，不能在新版计划下发布。
- 首次有效计划前禁止数据库探索的现有约束保持；允许计划有未决槽位，但不能靠全空 envelope 绕过必要内容检查。必要内容检查只检查请求/任务关联与有效声明，不假装自动证明语义完整。
- evaluate_candidate 不因为模型列出 selectedDecisionIds 就宣称 SQL 实现了它们；实际核对失败或缺覆盖需要返回明确记录。
- 工具重试须具有幂等键或等价去重机制；发布重试返回同一发布结果，不重复创建相互矛盾的 Receipt。

### 4.1 Fast-Path：状态迁移不等于模型往返

上述四个动作是概念性 Interface，不是每题必须完成的四轮打卡。P1 即引入可选组合路径，优先扩展现有工具参数或提供薄 adapter，不必等待 P5 全面重命名：

```text
开始：planProposal + initialExploration? → revisionId + evidence
结束：evaluate_candidate + deliverIfEligible → candidate / delivery
```

- Runtime 顺序登记计划、执行探索；首次计划失败时不得访问数据库。没有探索需要时允许省略，不增加凑流程的查询。
- 收敛组合先成功预览、核查精确候选、应用 Delivery Policy、生成披露，再发布。候选或修订不得在组合中被偷偷替换。
- 需要用户澄清或政策要求修订时，返回候选及行动要求，不执行发布。单纯 unsupported/inconclusive 默认披露，不强迫模型重写计划。
- 这是一个工具内部的受控顺序执行，不是并行调用有依赖的工具。开始与结束组合均须有幂等及中途失败语义。
- 查询 SQL、计划和选择已齐备的简单任务，协议目标为不超过 2–3 次串行模型—工具往返；不承诺复杂任务总轮次不超过 3。
- 分别计量 Assistant turns、工具调用、串行模型往返、探针/数据库调用与墙钟耗时。组合不能把多条 SQL 隐藏成一次 exploration 以绕过预算；所有实际探索与探针仍分别记账。
- 在 deadline 前预留发布时间，预留值由 P0 耗时基线冻结。余额不足时停止新增探索，按已有证据和既定政策交付或明确失败；不得降低身份/披露要求，不启动无界自动修复。

1. 保存当前工作区补丁及 hash，冻结源码、构建、Prompt、工具 schema、模型、方言解析器、预算和评分器版本。不得覆盖现有未提交改动。
2. 以 local032 已报告身份差异建立最小回归，定位 candidateBindingValid 的具体字段差异；不得通过放宽身份检查修复。
3. 建立现有发布完整性测试矩阵及固定评估题集。

6. 保存两份不可变检查点：当前状态 B0，以及完成 P0 必需发布修复后的 B1。后续阶段与 B1 比较，同时报告 B0→B1 的变化。

- exploration、伪造 hash、错误候选、旧版本、错误 Receipt 五类负例全部被拒绝。
- 同一合法候选重复发布的行为明确且测试稳定。
- Runtime、Server、Electron 相关构建及现有核心回归通过；既有跳过项单列。
- 基线运行有 manifest、完整题目清单、固定分母指标及工作区身份，可复现。
- B0/B1、确定性协议回放 fixture、Delivered/Correct Set 和实时 Smoke 报告均存在；P1 不得在这些前置条件未完成时启动。
- 通过第 13 节共同回归门槛；已知违规旧行为不纳入“必须保留”的合法交付合同。

### 交付物

基线 manifest、回归测试、字段级故障报告、能力矩阵。此阶段不得以错误率改善作为已验收结论。

## 6. Phase 1：收回证据与可信状态的自报权

依赖：Phase 0。

### 实施

1. 复用 TrustedEvidenceStore/submitProposal，补齐工具观察、文档及澄清证据登记。
2. 新模型 Interface 不接受自报 user_confirmed/evidence_supported。
3. 旧 envelope adapter 对无可信证据的升级请求拒绝或降级并返回显式诊断；两种动作按版本固定，不得静默降级。
4. 引入 Claim 与 Verification 记录，保留现有 hypothesisId 的迁移映射。
5. 证据状态变化必须生成新修订；旧验证记录不能自动验证新内容。
6. 落地第 4.1 节开始/收敛组合路径及预算记账。此阶段使用现有候选/披露能力，后续 P2/P3 在同一内部路径补强，不增加必需模型往返。
7. 建立任务级 protocolVersion 与持久化 schemaVersion；新旧 adapter 分别接入同一核心。工具 schema、Prompt、Host 和 Runner 的协议版本在任务创建时一次冻结。

### 验收（全部满足）

- 无证据自报确认、伪造 evidenceId、跨任务引用、过期/错 hash 引用的负例全部不能升级可信状态。
- “枚举存在所以代表已完成”的测试只能得到物理值存在的支持，业务映射保持未决。
- 真实澄清回答关联到准确 claim/decision，生成新版本，旧候选失效。
- 仅匹配题面 substring、仅有高 confidence、仅有 semantic_assessment supported 均不能自动建立 Hard Constraint。
- 进程恢复后证据、版本和核查关系保持；审计中无凭据泄露。
- 对该 Interface 的正负例与状态迁移测试全部通过。
- 简单 fixture 不因协议引入额外必需往返，并达到第 4.1 节目标；组合各故障点不能错发结果，超时与重试可恢复。
- 组合内实际探索/探针全部记账，预算耗尽不触发循环；已记录与基线的 turns、串行往返和耗时对比。
- 新旧 Host/Runner 协议合同通过；同一任务不能混用新旧可写状态。通过第 13 节共同回归门槛。

## 7. Phase 2：明确解释采用与未决选择

依赖：Phase 1。

### 实施

1. 引入 Decision/Alternative，分离“采用”与“被支持”。
2. 将当前 hypothesisRefs 转为明确的 adopted claim/decision 关联；旧字段只保留兼容投影。
3. 针对客户等权/订单加权、含税/未税、时间字段、NTILE 并列策略建立人工场景测试。
4. 明确三类策略：interactive 澄清；无交互 literal-with-disclosure；显式配置的严格策略。策略及版本入 Receipt。
5. 已发现且影响口径的未决选择在交互场景触发澄清，取消/超时不视为确认。
6. 实施下述离线选择策略；官方评分只对最终答案计分，披露完整不能代替 CSV 正确。

### 7.1 Offline Tie-Breaker：有限证据下明确选一个

策略名建议为 `literal-minimum-assumption-v1`。先做证据约束下的选择，再做确定性兜底：

1. 根据合格证据排除明确违反用户要求、权威定义或已成立反证的候选。模型自称“违背题面”不足以直接排除。
2. 对剩余候选优先采用有适用、非冲突的权威支持者。证据冲突无法解决时保留未决，不把简单引用数当支持强度。
3. 在证据不能区分时，按预先冻结的“额外假设向量”比较：未支持的总体排除/过滤、金额组成增项、额外加权或分母规则等。比较维度、顺序、缺失值处理写入策略版本；不按描述字数、confidence 或模型给候选的编号排序。只比较受支持的规范字段，不为此构建通用语义解析器。
4. 仍并列时使用已冻结的通用默认约定；没有适用约定或规范字段无法比较时，使用规范候选内容的稳定排序兜底。规范化版本固定，去除展示 ID/输入位置，去重后按规范序列排序；无法语义去重的同义改写属于已披露限制。
5. 保存输入快照/hash、规范化版本、逐项比较依据、selectedAlternativeId、selectionPolicyVersion、selectionReason，以及所有未选分支。第 3–4 步产生的选择一律为 `provisional_literal`，不得升格 confirmed。

“最少假设”中的语义分类仍可能依赖模型且可能出错；确定性仅承诺对同一冻结候选及证据输入稳定选择，不承诺不同模型生成相同候选，更不承诺命中 Gold。稳定排序是最后的任意兜底，其使用率必须单列。

禁止以 case ID、Gold SQL/CSV、官方得分反馈定制分支；规则只能在开发集上制定并于留出评测前冻结。默认只执行被选分支，不为每个 alternative 运行完整 SQL。所有候选均违反合格约束时返回明确无可用解释，不为凑 CSV 绕过约束。最终提交只提取一个有匹配 Receipt 的选定 CSV，不能按分支分数或文件发现顺序择优。

### 验收（全部满足）

- 互斥 alternatives 不能同时被选；选择不存在或已被替换的 alternative 被拒绝。
- 未采用解释不会被标记 refuted；采用临时解释不会变成 confirmed。
- SQL 明确绑定当前 revision 与选项，修改选择使既有候选失效。
- 交互 fixture 中的重要歧义全部进入澄清流程；用户取消、超时及不可用工具行为有明确测试。
- 无交互 fixture 全部记录 provisional_literal 和未决状态，无静默自我确认。
- 零假设的明确请求可以正常完成，不强迫生成备选项。
- 离线选择固定输入重复运行、改变候选排列/展示编号后结果一致；规范化与策略版本可回放。
- 含运费/不含运费、客户等权/订单加权、NTILE 并列规则 fixture 均记录明确选项及选择理由；证据不足不伪造确认。
- 评分提取器只提交选定候选，所有未选分支进入披露；无可用解释的失败保留在固定分母内。
- 选择器运行输入不含 Gold、官方分数或按 case ID 分支规则；分别统计默认约定/稳定排序兜底率及留出集选择正确率。
- 通过第 13 节共同回归门槛。

注意：以上是已知场景的机制验收，不代表自动歧义发现召回达到 100%。自然问题召回另由 Phase 6 测量。

## 8. Phase 3：统一自动披露与交付

依赖：Phase 2。

### 实施

1. 从候选绑定的计划与核查记录生成 Disclosure，不再仅从异常注册表生成。
2. CSV、内联、Server、Electron 使用同一 DeliveryEnvelope 规则。
3. Receipt 绑定 disclosureHash、policyVersion 与计划身份。
4. 交付数据与披露作为一组发布；披露不可用时不得返回误导性的“完整交付成功”。重试不重复发放。
5. CSV 重执行如无快照能力，明确披露数据时间及漂移风险；有快照能力则绑定快照。不得伪称内联与重执行导出是同一数据快照。

### 验收（全部满足）

- candidate 存在而 anomaly=0 的样例仍显示未确认口径。
- 检测 unavailable/inconclusive 不能显示为“全部通过”。
- CSV 与内联都能让用户直接看到或访问披露；不只写入日志。
- 披露引用其他候选、旧版本或内容 hash 不匹配时发布失败。
- 数据生成成功但披露失败的故障注入不产生完整成功 Receipt；重试后交付一致。
- “导出成功立即停止”场景无需模型额外自然语言补充也能完整披露。
- 四种 Host/交付组合通过共享合同测试；不支持的组合明确禁用，不能登记为通过。
- Spider2 CSV 仅含答案数据，披露位于独立附件/审计对象，不向官方答案列或行注入说明文字；提取器仍验证精确 Receipt。
- Fast-Path 自动生成披露，无额外必需模型往返；通过第 13 节共同回归门槛。

## 9. Phase 4：有界反证优先，不做完整语义对齐

依赖：Phase 2；推广依赖 Phase 3。

### 实施

将“明确计划”与“证明 SQL 实现计划”拆开。保留少量结构化字段以表达基础粒度、聚合层级、分母/权重、时间边界和 tie policy；它们用于解释选择与披露，不要求建立自然语言计划到任意方言 AST 的等价证明。

1. 在已支持字段上维护唯一规范表示，再生成七槽位文本与兼容 answerContract；未知字段保持未知，禁止两套独立可写语义源。
2. 仅启用注册过适用条件的局部反证规则；每条声明 ruleVersion、dialects、requiredEvidence、supportedShapes、probeBudget 与结果覆盖范围。
3. 优先复用 D1/D2 等实测证据，Risk Planner 按风险选择检查。没有命中只说明未发现该类反证，不能形成整体“SQL 符合计划”的 verdict。
4. parser/lineage/证据缺失返回 unsupported、unavailable 或 inconclusive；纯检测缺覆盖不触发发布阻断，也不要求模型为迎合 AST 模式重写 SQL。
5. 新增语义/反证检查先 shadow，按 ADR-0003 默认告知。继续保留既有身份完整性与合格确定性形状阻断，不因检测器开关放宽它们。
6. 完整聚合链对齐、通用分母证明、计划编译器移出本轮必需范围；若后续立项，单独评估覆盖、误报和成本。

### 反证资格示例

| 可疑现象 | 必须检查的前提 | 默认处理 |
|---|---|---|
| JOIN 后键重复 | 源键唯一、相关度量确受重复影响、没有后续去重/预聚合抵消 | 有证据的局部反证或异常告知，不凭 JOIN 形状阻断 |
| WHERE id <> 999 | 是否有业务文档授权，是否确实缩减目标总体；不能只看题面是否出现 | 证据不足记录待核查，不自动判未授权 |
| 外层无聚合 | 是否内层已经聚合、最终形状是否违反权威输出合同 | 仅合格的实际形状违规可按既定政策阻断 |

### 验收（全部满足）

- 客户等权与订单加权可表示为不同计划选择，但不把“任意 SQL 自动区分二者”列为本期验收承诺。
- 每条启用规则具有错误命中例、正确反例、合法近似结构、不支持例、证据不足例；固定 fixture 上预期行为全部通过，实际误报率由 Phase 6 测量。
- parser 不支持、空 expected 集、review reason 校验失败等不会被包装成已证实的 SQL 语义错误；分别记录内部能力故障，身份故障仍硬阻断。
- 预聚合/去重后的合法 JOIN、权威授权的排除条件、内层标量聚合不被简单特征误杀。
- 新增 shadow 检查开关不改变合法候选的发布授权，只改变观测与披露；合格形状与身份规则另测。
- 同一计划的七槽位/answerContract 投影一致；不支持字段不补造约束。
- 探针超预算停止且披露，实际调用全部记账；Server/Electron 同能力返回一致状态，跳过有 reason。
- 通过第 13 节共同回归门槛，不要求为通过测试扩展成通用 AST 白名单。

## 10. Phase 5：收敛 Answer Session 深模块与提示词

依赖：Phase 1–4 的合同稳定。

### 实施

1. 将版本、身份、核查调度、候选登记与披露收敛到统一 Interface 后面；Host 保留工具、存储和传输 adapter。
2. 外部使用 revisionId/candidateId 不透明句柄，内部保留 hash 全量验证。
3. 模型 Prompt 只强调解释、证据、重要歧义与行动选择；移除手抄 hash 和自报可信状态要求。
4. 修复现有空 filters 却绑定 /filters/0 的示例；所有 Prompt JSON 示例执行 schema/路径校验。
5. 旧接口设兼容期和删除条件；不维护两套默认协议。

### 验收（全部满足）

- 并发修订只有合法 base 可以提交，过期 base 返回显式冲突，不覆盖他人修订。
- 提交、执行、发布重试具有可测幂等行为；进程恢复后身份一致。
- 模型不需要提交 specHash，Runtime 仍拒绝旧修订/错误候选发布。
- 核心端到端测试经统一 Interface 完成；Host 共享同一合同测试。
- Prompt 示例全部可执行校验通过；不存在提示要求新字段但工具只接受旧字段的分裂。
- 接口复杂度对比报告列明模型必填字段、必须记忆的调用顺序和重复状态减少情况；不得仅以代码行数减少验收。
- 未迁移旧会话可只读审计或通过显式迁移恢复；没有证据的历史状态不能被补造为已验证。
- protocolVersion/schemaVersion 的旧读、新写、恢复及拒绝混用合同均通过；只有旧任务已排空或支持只读保留且回退演练通过，才删除旧 adapter。
- 通过第 13 节共同回归门槛。

## 11. Phase 6：效果验收与灰度推广

依赖：Phase 0–5 工程验收通过。

### 11.1 两类实验分开

A. 架构实验：冻结同一模型、预算、数据、评分器及基础任务说明，比较旧协议与新协议。工具/协议 Prompt 的变化是 treatment 本身，不能宣称两者 Prompt 完全相同。

B. 检测器消融：在同一新协议、同一 Prompt 下，仅开关新增风险检查，用于区分协议变化与检测能力的贡献。

固定预算建议先沿用 20 turns / 50 tools / 6 exploration / 300s；正式运行前验证预算适配两种协议并冻结。基础设施故障、超时、无发布均保留在固定分母中并分类报告，不择题重跑替换失败结果。

### 11.2 数据集与指标

- 现有 10 题仅用于 smoke，不作为推广证据。
- 使用冻结的可运行较大题集，建议至少 100 题；开发案例与留出集分离。135 题 Spec 标签不能当作 LLM 新计划质量的现成评分，需另行盲标。
- 至少三次配对运行，报告随机波动；置信区间按题目聚类，不能把重复运行当作独立题目扩大样本。
- 人工盲评重要歧义发现、证据支持是否恰当、采用解释与披露是否一致；至少双标注并裁决分歧。
- 官方 SQL EX、E2E EX、SQL/CSV 覆盖、完整性失败、确认越权、漏披露、成本、平均及 P95 延迟全部报告。
- 单列离线分支选择正确率及默认/任意兜底使用率；选择正确率使用有独立裁决标签的歧义子集为分母，不以披露完整或全题 EX 代替。
- 单列 Assistant turns、串行模型往返、实际探索/探针次数、Fast-Path 覆盖率与 Timeout 率。按正确选择但执行错误、选择错误、协议故障、预算耗尽分类归因。
- 追踪冻结 Correct Set 的逐题正确→错误迁移，以及 Delivered Set 的逐题可交付→失败迁移，不只报告整体覆盖率。

### 11.3 建议推广门槛（实验前批准并冻结）

1. 完整性与权限：负例合同测试 100% 通过；正式样本中无越权确认、探索发布或错版本交付。
2. 披露：人工标注“已采用且未确认”的已识别口径，漏披露率为 0；隐藏歧义漏检率单独报告，不混入该分母。
3. 正确率：treatment 平均固定分母 E2E EX 不低于 control，配对差值 95% 置信区间下界不低于 -3 个百分点。达不到统计把握则扩大样本，不能凭点估计宣布非劣。
4. 可交付性：SQL/CSV 覆盖下降不超过 2 个百分点，新增系统性发布失败为 0。
5. 成本：平均工具调用和平均 token 成本增量分别不超过 15%，P95 延迟增量不超过 20%。超过时需单独业务批准，不自动推广。
6. 语义收益：在独立盲标风险集，重要歧义识别召回相对基线提升且 precision 不下降；报告样本数和区间，不只报告命中条数。
7. 基线回归：第 13 节确定性合同无非预期回退；所有实时 Smoke 退化已归因处理，不允许用其他题的提升掩盖确定性的协议损坏。随机模型逐题差异进入配对统计，不要求单次运行机械零回退。
8. 预算：简单 Fast-Path fixture 达到 2–3 次串行往返且无新增必需协议往返；正式集 Timeout 率点估计不得高于 control，区间和原因同时报告。观测不足时保持实验状态。

通过这些门槛只允许宣称“本次条件下达到推广要求”，不等于证明任意业务问题正确或证明准确率显著提升。

### 11.4 灰度与回退

- 按任务固定分配 legacy/new，任务中途不得切换协议或放宽身份检查。
- 先内部只读任务，再小比例产品任务；灰度比例与观察窗口由发布负责人预先冻结。
- 发现错候选交付、虚假用户确认或漏披露，立即暂停新任务进入新协议，保留已有任务审计。
- 回退到上一可信版本，不回退到无身份检查发布。
- 新格式任务无法由旧版本恢复时，只读保留并提示用户重新发起，不丢弃或伪造状态。

## 13. 测试矩阵与阶段关闭规则

必须覆盖：

```text
身份：正确 / 伪造 / 过期 / 跨任务 / 恢复
证据：权威 / 观察 / 推断 / 缺失 / 冲突
选择：无歧义 / 单一临时选择 / 互斥选项 / 用户取消
SQL：支持 / 不支持 / 证据不足 / 明确不一致
交付：内联 / CSV × Server / Electron
运行：正常 / 超时 / 重试 / 并发 / 中途故障
```

每阶段关闭需要：

1. 验收条目逐项状态及证据路径，不允许以“实现完成”替代验收。
2. 对应提交或工作区补丁 hash、构建命令、测试命令与实际输出。
3. 已知残余风险、跳过项及原因；必需项未执行则阶段保持未完成。
4. 实现者之外的复核记录；复核不是语义正确性证明。
5. 后续阶段若改变前序合同，重新运行受影响验收。
6. 每阶段都必须通过以下共同回归门槛；P0 负责建立并校验基线，P1 起与冻结的 B1 比较。

### 13.1 No Regression on Baseline Delivered Set：三层回归

| 层次 | 固定对象 | 阶段通过条件 |
|---|---|---|
| 确定性协议回放 | 合法工具轨迹、受控 SQL 结果、候选、证据和 Receipt 合同 | 非预期交付回退为 0；规范化结果内容/hash 不变，允许预先声明的元数据扩展 |
| 实时 Smoke | 冻结题集、Host、Runner、模型配置与预算 | 每项退化有原因与证据；确定性协议故障必须修复；疑似随机性按预先冻结的配对复跑方案验证，保留全部尝试，不择优替换 |
| 全量配对模型评测 | 固定较大题集及独立评分 | 按 Phase 6 非劣、覆盖、成本与超时门槛；只在阶段约定检查点/最终推广运行，不强迫每次小改动跑全量 |

- Delivered Set 与 Correct Set 分开维护。机制回放保证已知合法流程不坏，不保证模型重新生成同一 SQL；全量正确性仍以固定分母官方评分及盲标为准。
- 安全修复导致的预期拒绝必须提前登记具体 fixture、理由、批准人和受影响指标；不得在看到回归后补写豁免，也不得为了守住旧基线保留越权漏洞。
- 每阶段提交协议往返和预算差异报告；新增必需往返须明确必要性、成本与批准，不能隐藏在工具内部不记账。

### 13.2 双轨过渡的限制

- 双轨只存在于任务级 adapter，不存在于同一任务的两份可写计划。任务固定 protocolVersion，持久化记录固定 schemaVersion。
- 存储变更优先增量兼容；破坏性迁移必须提供备份、恢复演练和旧版本行为说明。
- Server、Electron、Runner 的版本组合列入矩阵；不兼容组合在启动/恢复时明确拒绝，而不是执行到导出才报身份错误。
- 旧 trace 的回放只允许显式 adapter 补齐协议映射，不能补造业务证据或确认状态；无法合法迁移的 trace 保留为历史观测，不算新协议正例。
- 任何阶段回退都保留证据与审计，不能通过关闭身份检查、跳过披露或覆写旧状态恢复表面覆盖率。

## 14. 推荐实施顺序

```text
P0 基线与发布故障
 → P1 证据与状态所有权 + 低轮次组合路径
 → P2 解释选择 + 离线 Tie-Breaker
 → P3 自动披露
 → P4 有界反证核查
 → P5 Interface/Prompt 收敛
 → P6 配对评估与灰度
```

第一批价值交付以 P1–P3 为核心：先防自我确认和漏披露，同时守住预算与离线最终答案选择。P4 只交付有适用前提的局部反证能力，完整语义对齐和计划编译器不属于本轮必需范围。每阶段先守住确定性合法交付，再测真实准确率；不能用审计完整替代答题正确，也不能为了“优雅”同时重写 Spec、SQL 执行器、存储及所有 Host。
