# 未决假设提醒与处置最小架构落地实施方案

> 状态：实施中（按用户确认修订）
>
> 目标：以最小改动减少“假设已登记但被 Agent 忘记、SQL 静默选择口径”的问题；允许 exploration 取得处置证据，但在候选假设仍未处置时阻塞 result SQL 与发布/导出，不建设通用反例引擎。
>
> 典型案例：Spider2 `local061` 的 H6。

---

## 1. 一页结论

本方案只增加四项能力：

```text
Spec 结构一致性规范化
+ 未决假设最多三次提醒 Hook
+ 带 handled/unhandled 标签的假设处置派生视图
+ 未处置假设的 result SQL 与发布/导出阻塞
```

职责分配：

```text
Hook                 负责让未决假设在正确时机重新可见
现有 Verification    负责记录可信证据支持/反驳
现有 Decision         负责记录临时或用户选择的解释
派生 Disposition      负责回答“这个假设最终如何被处理”
Artifact Binding      负责固定结果引用的假设与选择
Result Boundary       负责在仍有 unhandled 假设时阻塞 result SQL 与发布/导出
Delivery Policy       负责已处置候选的后续发布策略
```

本方案不承诺机器判断反例质量，也不证明任意 SQL 语义正确。它首先解决更小但明确的问题：

> Agent 不能再把 candidate hypothesis 登记后完全遗忘；Runtime 必须在结果及回执中明确记录该假设是已验证、临时采用，还是仍未解决。

## 2. 背景问题

当前理想链路是：

```text
发现不确定性
→ 定义互斥解释
→ 设计能区分解释的最小反例
→ 取得并登记证据
→ 判断证据只能证明现象，还是足以选择业务口径
→ 修订 Answer Spec / 请求澄清 / 选择临时解释
→ 将最终 SQL 绑定到所选解释
→ 按交付策略发布或阻断
```

当前 Runtime 已经分别具备 Answer Spec、Hypothesis、Decision、Evidence、Verification、Artifact Binding、Disclosure 和 Delivery Policy，但缺少一个低成本机制，把“仍未处理的 candidate hypothesis”重新送回 Solver 的注意范围。

`local061` 的实际表现：

```text
H6 被登记为 candidate
→ Agent 检查到 2019 聚合值没有零
→ 忽略 2019/2020 产品月份集合不一致
→ 没有修订 Spec
→ 没有建立 Decision
→ INNER JOIN 静默采用交集总体
→ H6 未绑定最终 Artifact
→ 仅在 disclosure 中出现
```

## 3. 设计约束

### 3.1 必须遵守

1. 遵守 ADR-0003：检测和提醒默认只告知，不拥有业务裁决权。
2. Spider2 无交互评测允许在存在未处置假设时继续 exploration；result SQL、CSV 导出与内联发布必须阻塞，直到所有候选假设均派生为 handled。
3. 不增加通用 SQL 语义证明器。
4. 不增加按题型命名的检测器，例如专为 local061 新增阻断型 `cross_period_set_mismatch`。
5. 不要求 Agent 重复探索直到“证明”业务意图。
6. Hook 不绑定固定触发阶段；同一 taskId + revisionId + hypothesisSet 最多注入一次，每任务最多注入三次。
7. Runtime 不接受 Agent 自报 `evidence_supported` 或 `user_confirmed`。
8. 放行、提醒或披露均不得表述为“已验证正确”。

### 3.2 非目标

本期不实现：

- 自动生成最小反例；
- 自动判断反例是否具有区分力；
- 任意 SQL 与业务解释的完整等价性证明；
- 新的 LLM Reviewer 运行时裁决路径；
- 大规模 Witness Algebra；
- 阻塞 exploration 查询；
- 自动将观测数据升级为业务定义。

## 4. 核心领域模型

### 4.1 不新增可写的 HypothesisDisposition 真源

为控制复杂度，`HypothesisDisposition` 不作为新的可写领域对象持久化，而是由现有状态派生：

- `Hypothesis.status`；
- Runtime-owned Verification；
- Decision selection；
- Decision alternative 的 `legacyHypothesisRefs`；
- 当前 Spec revision。

建议新增只读类型：

```ts
export type HypothesisDispositionStatus =
  | "user_confirmed"
  | "evidence_supported"
  | "rejected"
  | "provisional_selected"
  | "unresolved";

export interface HypothesisDispositionView {
  readonly hypothesisId: string;
  readonly revisionId: string;
  readonly status: HypothesisDispositionStatus;
  readonly handlingStatus: "handled" | "unhandled";
  readonly facetPaths: readonly string[];
  readonly verificationRefs: readonly string[];
  readonly selectedDecisionRef?: {
    readonly decisionId: string;
    readonly alternativeId: string;
  };
}
```

派生顺序（与当前 `projectedHypothesisStatus` 的反驳优先语义保持一致）：

```text
存在 refuted Verification                    → rejected
存在用户确认 Verification                    → user_confirmed
存在合格 formal-rule Verification            → evidence_supported
被 selected Decision alternative 引用        → provisional_selected
其他 candidate                               → unresolved
unresolved                                    → handlingStatus = unhandled
其他 disposition                              → handlingStatus = handled
```

不得根据 Solver 的自然语言声明改变 disposition 或 handlingStatus。

### 4.2 为什么采用派生视图

相比新增一套可写状态机，派生视图具有以下优势：

- 不产生第二份真源；
- 复用现有 Claim/Verification/Decision；
- 避免 Disposition 与 Hypothesis 状态漂移；
- 恢复运行时可以从持久化状态重建；
- Artifact/Receipt 可以保存当时的不可变快照。

## 5. Spec 结构一致性规范化

### 5.1 不变量

如果一个 `candidate` hypothesis 绑定到某七槽位，该槽位不能同时保持 `explicit`。

非法状态示例：

```text
H6.status = candidate
H6 binding = /metric
facetStatus.metric = explicit
```

### 5.2 建议动作：确定性规范化而非默认抛错

为避免 Spider2 因重复 Spec 错误进入非交付，Runtime 在接受 revision 时执行：

```text
candidate hypothesis bound to /<facet>
+ facetStatus.<facet> = explicit
→ facetStatus.<facet> = hypothesis
```

规范化必须：

1. 在计算 Spec hash 前完成；
2. 写入实际持久化 revision；
3. 通过工具返回告知 Agent；
4. 记录规范化原因和 hypothesis ID；
5. 不修改 hypothesis statement；
6. 不选择任何业务解释。

工具返回示例：

```text
[ANSWER_SPEC_NORMALIZED]
metric: explicit → hypothesis
reason: candidate hypothesis H6 is bound to /metric
```

### 5.3 路径读取

绑定路径来自 `hypothesisBindings`，不是 Hypothesis 自身：

```ts
for (const binding of hypothesisBindings) {
  const hypothesis = hypothesesById.get(binding.hypothesisId);
  if (hypothesis?.status !== "candidate") continue;

  for (const path of binding.paths) {
    const facet = facetFromJsonPointer(path);
    if (facet && facetStatus[facet] === "explicit") {
      facetStatus[facet] = "hypothesis";
      normalizations.push({
        code: "FACET_STATUS_CANDIDATE_NORMALIZED",
        facet,
        hypothesisId: hypothesis.id,
      });
    }
  }
}
```

### 5.4 严格校验

单元测试和开发诊断可以提供严格模式，将同一矛盾抛为：

```text
FACET_STATUS_CONFLICT:<facet>:candidate=<hypothesisId>
```

首期 Spider2 运行时默认采用规范化，不采用不可恢复异常。

## 6. 未决假设提醒 Hook

### 6.1 Hook 定位

复用现有：

```text
prepareNextTurnWithContext
```

新增开关：

```ts
interface AssuranceHookSwitches {
  readonly informOnUnresolvedHypotheses?: boolean;
}
```

默认策略：

- Spider2 实验 arm：开启；
- 产品端：先以 Shadow/可配置方式开启；
- Hook 失败：fail-open，不影响原工具结果与交付。

### 6.2 数据来源

Hook 只读取 Runtime-owned 派生视图：

```text
getAnswerPlanView(taskId, revisionId)
+ projectedHypothesisStatus
+ derived HypothesisDispositionView
```

不得直接相信模型在消息中声称“已验证”。

### 6.3 触发条件

Hook 不绑定固定阶段。每次 `prepareNextTurnWithContext` 均按当前 Runtime 状态判断，满足以下条件时注入：

```text
存在 disposition.handlingStatus = unhandled
AND 当前任务尚未发布
AND 当前 taskId + revisionId + hypothesisSet 尚未注入
AND 当前任务累计注入少于三次
AND Hook 开关已启用
```

这允许早期 revision 获得提醒，也允许探索后新出现或发生变化的关键假设在后续 revision 再次提醒。

### 6.4 去重键与预算

去重键：

```text
SHA256(taskId + revisionId + sorted(unresolvedHypothesisIds))
```

约束：

- 同一去重键最多注入一次；
- revision 或未处置 hypothesisSet 变化后允许重新注入；
- 每任务累计最多注入三次；
- hypothesis 得到 Verification、被反驳或被 Decision 选择后变为 handled，不再提醒；
- 不触发额外 LLM 调用；
- 不自动触发探索 SQL；
- 成功导出后不再注入。

### 6.5 注入消息格式

```text
[UNRESOLVED_HYPOTHESES]
当前 Answer Spec 存在未处置假设：
- H6 handling=unhandled /metric: <statement>
重新检查这些假设是否改变答案；是否违反业务语义先于物理实现原则？请查阅题目和参考文档。
[/UNRESOLVED_HYPOTHESES]
```

### 6.6 消息边界

Hook 只能告知：

- 哪些 hypothesis 仍未解决；
- 影响哪些槽位；
- 是否存在可信 Verification；
- 可采取哪些有界动作。

Hook 不能：

- 将 candidate 改为 supported；
- 判断 hypothesis 正确或错误；
- 自动新增过滤、补零、Join 或分母政策；
- 要求无限探索；
- 自行执行 result SQL 或发布阻断；阻断由独立 Result Boundary 根据 handlingStatus 确定性执行；
- 声称没有反证即得到验证。

### 6.7 Result Boundary 阻塞

在当前 evidence-plan-v2 revision 中，只要存在：

```text
hypothesisDisposition.handlingStatus = unhandled
```

Runtime 必须：

- 允许 `query_database(mode="exploration")`；
- 在执行数据库 SQL 前阻塞 `query_database(mode="result")`；
- 阻塞未处置 Result Artifact 的 `export_query` 与 `publish_query_result`；
- 返回未处置 hypothesis ID、facetPaths 与 `nextAction=update_answer_spec`；
- 不把阻塞表述为假设正确或错误。

Agent 可通过用户确认、合格 Verification、反驳或引用该 hypothesis 的 selected provisional Decision 将其派生为 handled。仅修改自然语言或自报“已验证”不能解除阻塞。

## 7. 结果 Artifact 绑定

### 7.1 Candidate hypothesis 引用完整性

经过 Spec 规范化后，所有绑定到 `facetStatus = hypothesis` 的 candidate hypotheses 都应自动进入结果 Artifact 的 `hypothesisRefs`。

对 local061，预期从：

```json
["H1", "H2", "H3"]
```

变为至少包含：

```json
["H1", "H2", "H3", "H4", "H5", "H6"]
```

这表示该候选结果依赖这些未确认解释，不表示这些解释已验证。

### 7.2 Disposition 快照

Result Artifact 建议保存派生快照：

```ts
readonly hypothesisDispositions?: readonly HypothesisDispositionView[];
```

快照用途：

- 防止后续 revision/Verification 改变历史候选含义；
- 支持 Receipt 和离线 replay；
- 区分 unresolved、provisional 和 verified；
- 不需要创建新的可写状态表。

### 7.3 Decision 绑定

如果 Agent 为 H6 提交 Decision，并由无交互策略选择 provisional alternative：

```text
H6 disposition = provisional_selected
selectedDecisionRef = D-missing-policy / ALT-intersection
```

Artifact 继续使用现有 `selectedDecisionRefs` 和 selection input hash。

如果 Agent 没有建立 Decision：

```text
H6 disposition = unresolved
H6 handlingStatus = unhandled
```

Benchmark 可继续 exploration，但 result SQL 与发布/导出均被阻塞。

## 8. Disclosure 与审计

### 8.1 Disclosure

现有 `candidate_hypothesis` disclosure 保留，并增加处置状态：

```json
{
  "kind": "candidate_hypothesis",
  "hypothesisId": "H6",
  "disposition": "unresolved",
  "facetPaths": ["/metric"],
  "message": "候选假设 H6 尚未验证或选择"
}
```

若已进行 provisional selection：

```json
{
  "kind": "provisional_decision",
  "hypothesisId": "H6",
  "decisionId": "D-missing-policy",
  "alternativeId": "ALT-intersection"
}
```

### 8.2 Hook 审计

扩展 `HookFiredEvent` 的有界元数据：

```ts
interface HookFiredEvent {
  // 现有字段保持
  readonly subjectIds?: readonly string[];
  readonly revisionId?: string;
  readonly reasonCode?:
    | "UNRESOLVED_HYPOTHESES_PRESENT"
    | "UNRESOLVED_HYPOTHESES_ALREADY_INJECTED";
}
```

不得在 telemetry 中记录原始 SQL、结果行或完整 hypothesis statement；只记录稳定 ID。

Trace 至少能回答：

```text
哪个 revision 存在未决 hypothesis？
Hook 是否注入？
注入了哪些 ID？
Agent 后续是否修订 Spec？
最终 Artifact 的 disposition 是什么？
```

### 8.3 不得把提醒计为验证

评测和产品展示必须区分：

```text
hook_injected
hypothesis_dispositioned
hypothesis_verified
```

三者不能互相替代。

## 9. 不同环境的动作策略

### 9.1 Spider2 无交互 Benchmark

默认：

```text
unhandled hypothesis
→ 按 revision + hypothesisSet 去重，最多注入三次 Hook
→ exploration 继续可用
→ Agent 提交 decisionProposals 时可使用 provisional literal selection
→ 未形成 Verification/Decision 时保持 unhandled
→ Result Boundary 阻塞 result SQL 与发布/导出
→ handled 后 Artifact 绑定 disposition 与 Decision
```

禁止：

- 对同一去重键重复提醒；
- 因没有澄清能力进入无限等待或探索；
- 绕过 handlingStatus 阻塞执行 result SQL；
- 将 unresolved/unhandled 标记为 Approved。

### 9.2 交互式业务环境

如果 clarification capability 可用：

```text
material unresolved
→ Hook 告知
→ Agent 可调用 ask_user_clarification
→ 用户选择产生可信 Verification/Decision
```

Hook 不自行决定假设内容，但 Result Boundary 对 unhandled 状态统一阻塞；hypothesis handled 后，是否允许带 provisional disposition 发布仍由显式产品 Delivery Policy 决定。

### 9.3 状态阻塞与语义裁决的边界

`unhandled` 阻塞是生命周期完整性约束，不裁决某个假设正确或错误。只要用户确认、合格证据、反驳或 selected provisional Decision 形成明确处置，Result Boundary 即可放行；后续 Review 与 Delivery Policy 继续独立工作。

## 11. 实施阶段

### Phase 0：冻结回放与指标

1. 保存 local061 当前 Trace 和最终 Artifact 状态；
2. 建立最小回放断言：H6 未提醒、未绑定 Artifact、仅 disclosure；
3. 冻结固定 10 题配置、模型、预算和题单；
4. 记录当前交付率、正确率、Turns、Tool Calls 和 Token。

### Phase 1：Spec 一致性规范化

实现：

```text
candidate binding + explicit facet
→ hypothesis facet
```

验收：

- local061 H6 使 `metric` 规范化为 `hypothesis`；
- Spec hash 基于规范化结果；
- Agent 收到明确 notice；
- 不新增数据库调用；
- 不降低现有交付能力。

### Phase 2：最多三次提醒 Hook

实现：

- unresolved disposition 读取；
- `prepareNextTurnWithContext` 注入；
- revision 去重；
- Hook telemetry；
- feature flag。

验收：

- local061 在相关 revision 中看到 H6 提醒；
- 同一 taskId + revisionId + hypothesisSet 不重复注入；
- revision 或未处置假设集合更新后可重新注入；
- 每任务最多注入三次；
- verified/rejected hypothesis 不注入；
- Hook 失败不影响查询与导出。

### Phase 3：Artifact/Receipt 处置快照与 Result Boundary

实现：

- 派生 disposition 与 handled/unhandled；
- Result Artifact 快照；
- unresolved result SQL 与发布/导出阻塞；
- Disclosure 展示；
- Decision binding 兼容。

验收：

- local061 最终 Artifact 必须包含 H6；
- 没有 Decision 时显示 `unresolved`；
- 有 provisional Decision 时显示 `provisional_selected`；
- 不把两种状态标记为 verified。

### Phase 4：同配置 A/B

至少运行：

```text
Control：informOnUnresolvedHypotheses=false
Treatment：informOnUnresolvedHypotheses=true
```

保持：

- 同题单；
- 同模型；
- 同预算；
- 同日运行；
- 不逐题择优重跑。

若 Treatment 没有改善 silent-choice 或正确率，且增加 Turns/Token，应停止扩展，不继续建设更复杂体系。

## 12. 测试计划

### 12.1 Answer Spec 单元测试

- candidate 绑定 `/metric` 且 metric explicit → 规范化为 hypothesis；
- candidate 绑定 `/filters/0` → filters 规范化为 hypothesis；
- rejected hypothesis 不触发规范化；
- 一个 candidate 绑定多个 facet → 全部规范化；
- 未知 hypothesis ID、非法路径继续拒绝；
- 规范化前后输入对象不被原地修改；
- Spec hash 对规范化结果稳定。

### 12.2 Disposition 单元测试

- 无 Verification/Decision → unresolved；
- user clarification → user_confirmed；
- formal rule → evidence_supported；
- refuted Verification → rejected；
- selected provisional alternative 引用 H6 → provisional_selected；
- 未选择 alternative 不得产生 provisional_selected；
- revision 变化不复用旧 disposition；
- unresolved 显式派生为 `handlingStatus=unhandled`；其余 disposition 显式派生为 `handlingStatus=handled`。

### 12.3 Hook 单元测试

- 无 unresolved hypothesis → 不注入；
- 有 unresolved hypothesis → 注入；
- 同 revision 第二次 → 不注入；
- 新 revision 或未处置集合变化 → 可重新注入；
- 每任务第四个不同去重键 → 不注入；
- Hook switch 关闭 → 不注入；
- getter 抛错 → fail-open；
- 不触发 interpretation planner；
- 不执行 SQL；
- 不改变原消息顺序，只追加一条 custom context message；
- Hook telemetry 只含 ID，不含原始 SQL/行数据。

### 12.4 Artifact/Receipt 集成测试

- result Artifact 自动绑定所有 required candidate hypotheses；
- disposition 快照与 Spec revision 一致；
- provisional Decision refs 精确绑定；
- 旧 revision Artifact 仍按现有 stale 规则失效；
- unhandled 时 exploration 仍执行；
- unhandled 时 result SQL 在数据库执行前阻塞；
- 带 unhandled 快照的 Artifact 禁止 export 与 inline publish；
- provisional Decision 使假设变为 handled 后允许结果与发布；
- disclosure 包含 H6 及 disposition。

### 12.5 local061 回放测试

给定：

```text
H6 candidate → /metric
metric initially explicit
无可信 Verification
无 decisionProposals
```

必须观察：

```text
metric 自动规范化为 hypothesis
→ update_answer_spec 返回 H6 handlingStatus=unhandled
→ Hook 注入 H6 unhandled
→ exploration 仍允许执行
→ unhandled result SQL 被阻塞且未执行数据库查询
→ Decision 选择后 H6 = provisional_selected / handled
→ 新 result Artifact 与 Receipt 绑定 H6 及 Decision
→ 允许 CSV 导出但不得标记 verified
```

增加一个邻近正例：没有 candidate hypothesis 的简单聚合查询不得收到提醒，避免所有任务普遍增加上下文。

## 13. A/B 指标与验收门槛

### 13.1 必报指标

| 指标 | 含义 |
|---|---|
| Hook eligible cases | 存在 unresolved hypothesis 的题数 |
| Hook injection rate | eligible 中实际注入比例 |
| Revision response rate | 注入后 Agent 是否修订 Spec |
| Decision response rate | 注入后是否新增 Decision |
| Unresolved-at-result rate | 最终结果仍 unresolved 的比例 |
| Hypothesis binding coverage | 最终 Artifact 引用未决 hypothesis 的比例 |
| Silent-choice proxy | 有 candidate 但 Artifact 无 hypothesis/Decision binding 的比例 |
| Delivered rate | 合法 SQL/CSV 交付比例 |
| Official correctness | 官方执行正确率 |
| Mean/P95 turns | 回合成本 |
| Mean tool calls | 工具成本 |
| Mean tokens/latency | 上下文与时延成本 |

### 13.2 最低验收

固定 10 题 Treatment 相对 Control：

- Hook eligible case 的注入率为 100%；
- 同一去重键不重复注入，每题注入不超过三次；
- unhandled result SQL 的物理执行次数为 0；
- unhandled Artifact 的 export/publish 成功次数为 0；
- 形成 Verification 或 selected provisional Decision 后可恢复结果执行与交付；
- candidate hypothesis 的 Artifact binding coverage 为 100%；
- 必须报告 Delivered rate、`not_published`、max-turns、Turns、Tool Calls 与 Token 变化，但不再以“unhandled 仍可交付”为验收条件；
- 如果正确率不升且成本显著增加，不继续扩展提醒机制。

固定 10 题只用于机制 Smoke，不足以证明总体收益；后续必须使用独立留出集。原“一次性提醒且 unresolved 默认可交付”的 A/B 结果不能代替本修订版本的验证。

## 14. 风险与控制

| 风险 | 控制 |
|---|---|
| Hook 增加 Token | 每去重键最多一次、每任务最多三次；消息有长度上限 |
| Agent 形式主义回应 | 不把自然语言回应计为 Verification；只看 Runtime 状态 |
| Agent 继续忽略 H6 | exploration 保持可用；result SQL 与发布/导出阻塞并返回待处置 ID |
| 规范化粗化整个 facet | 首期接受保守降级；不据此阻断 |
| candidate 数量过多导致消息长 | 限制条数，剩余只列 ID；完整内容保留在 Spec |
| 与 anomaly interpretation Hook 重复 | 两种 Hook 独立开关、独立去重；首期不触发额外 planner |
| 产品端误认为提醒等于验证 | UI/Receipt 明确区分 injected、dispositioned、verified |
| Hook 抛错影响主流程 | 捕获异常并 fail-open |
| Benchmark 交付死锁 | exploration 永不因 unhandled 阻塞；最多三次提醒；返回明确 nextAction |

## 15. 回滚方案

本方案按独立开关交付：

```json
{
  "hooks": {
    "informOnUnresolvedHypotheses": true
  }
}
```

回滚只需关闭该 Hook，不修改：

- Query execution；
- Artifact identity；
- Publication Receipt；
- 现有 anomaly detectors；
- Delivery Policy。

Spec 一致性规范化应单独开关和 A/B，避免 Hook 与规范化效果无法归因。

---

## 16. 后续升级条件

只有满足以下条件之一，才考虑增加 Runtime Fact Card 或通用反例能力：

1. Hook 注入率达到预期，但 Agent 仍高比例忽略 material hypothesis；
2. Agent 经常把“没有零值”等局部观察错误当作完整验证；
3. 多个独立留出题重复出现同类可机器观测错误；
4. 可定义高精度、有界、非题型专用的证据算子；
5. A/B 表明额外事实注入带来净正确率收益且成本可接受。

未满足前，不新增复杂 Detector 或 Witness Engine。

## 17. 最终验收定义

本期完成不意味着已经建立完整的自动假设验证体系。完成标准是：

```text
所有 candidate hypotheses 在 Spec 中保持结构一致
→ 每项显式派生 handled/unhandled
→ 未处置状态按 revision + hypothesisSet 去重且每任务最多提醒三次
→ Agent 不能自报验证
→ unhandled 仅允许 exploration，result SQL 与发布/导出被阻塞
→ handled 后最终 Artifact 明确绑定依赖的 hypotheses/Decisions
→ Receipt 明确记录 verified/provisional/rejected
```

对 local061，最低合格结果不是“系统自动找到 Gold 口径”，而是：

> H6 不再被 `metric=explicit` 隐藏；Agent 显式看到 H6 为 unhandled；exploration 可继续；result SQL 在 H6 未处置时被阻塞；Agent 查阅题目和参考文档并形成 Verification 或 provisional Decision 后，新的 Artifact 和 Receipt 明确绑定其处置结果。
