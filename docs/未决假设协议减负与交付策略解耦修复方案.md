# 未决假设协议减负与交付策略解耦修复方案

> 状态：待评审，未实施。本文只提出修复设计，不表示现有运行协议已经变更。
> 范围：协议减负、执行与交付策略解耦、预算耗尽后的有界处置、测试与灰度验收。
> 明确排除：上下文压缩、历史裁剪、滚动摘要、Token 窗口管理、模型生成参数调整和截断恢复。后者另案处理。

## 1. 结论与修复目标

**保留证据权威和候选身份约束，取消“所有假设必须先变成 handled，才能形成结果候选”的普遍前置条件。模型表达业务解释，Runtime 维护机械一致性，Delivery Policy 决定未决解释能否交付。**

本次不建设新的语义裁判，不承诺自动找到 Gold 口径，不通过重复提醒或更多元数据表单提高形式合规率。

目标：

1. 模型只通过 `uncertainties` 登记不确定问题与选项，不再选择 Hypothesis/Decision 对象类型，也不重复填写 Runtime 可确定性派生的向量、状态和兼容映射。
2. 安全且口径已具体化的只读查询能够形成私有结果候选，不被普通未决假设普遍阻断。
3. 重大总体歧义保持真实未决；执行某个解释不等于该解释已被证实或 Decision 已被选定。
4. 交互、带披露交付和严格环境按显式政策采取不同动作，不靠 Hook 开关间接决定交付。
5. 没有新证据、预算不足或无法澄清时，进入确定的下一步，而不是无限表单重试。
6. inline、CSV、重执行和恢复路径使用同一政策实现，保持身份校验和可审计性。

## 2. 依据与结论边界

### 2.1 已有材料

- [local017 系统设计缺陷诊断](local017系统设计缺陷诊断.md)：报告了多轮协议处置、工具参数截断和最终未交付链路。
- [未决假设提醒与处置最小架构验收报告](未决假设提醒与处置最小架构验收报告.md)：工程机制通过，但最终版本完整同配置 A/B 未完成；reminder-only A/B 成本增加，正确率未改善。
- [探索证据桥与总体决策完整性](implementation/answer-plan/phase3b-evidence-population-hardening.md)：保留观测证据权威边界与 material population stable-order guard。

证据只支持当前机制存在成本与非交付风险，不证明放开普通未决阻断就能提高业务正确率。local017 的精确故障链路应以实施前回放为准。

### 2.2 当前代码确认的事实

- `tools-catalog.ts` 同时要求模型提交 `assumptionProfile` 和 `assumptionVector`。
- `decision-selection.ts` 已有 `deriveAssumptionVector()`，仍校验调用方提交的重复计数。
- `query-assurance.ts` 的 `assertNoUnhandledHypotheses()` 在多个阶段执行；`assertResultDecisionExecutable()` 另有 Decision 可执行性检查。
- `agent-assembly.ts` 还存在工具层未决阻断和 Decision 检查，不能只改底层其中一处。
- `assurance-hooks.ts` 的提醒开关与上述阻断独立；关闭提醒不等于允许执行。
- 底层已形成部分具体 integrity issue，但工具回执主要展示概括性的 selection reason。

### 2.3 ADR 冲突须显式处理

当前 accepted `ADR-0003` 第 3 条明确允许 `unhandled` 阻断 result/发布，第 4 条禁止稳定排序关闭重大总体平局。因此本方案不是单纯“恢复当前 ADR”，而是修改其中的生命周期阻断决策。

实施前新增后继 ADR，明确取代 ADR-0003 第 3 条中的普遍未决阻断，保留第 4 条的稳定排序限制，并澄清 ADR-0001 的环境化 Delivery Policy。同步更新 `CONTEXT.md`、系统提示词和协议文档，不能只改代码。

`uncertainties` 是本方案拟议的模型协议投影，不是当前已有领域术语，也不是第三套可信状态机。实施时在后继 ADR 和 `CONTEXT.md` 明确其与 Hypothesis、Ambiguity、Decision、Interpretation 的映射；内部领域对象仍承担原有职责。

## 3. 不变的安全与语义约束

以下约束不因本次修复而放宽：

1. 用户澄清、业务定义、Schema 和观测数据继续遵守 Evidence Authority；Gold 不进入运行时选择。
2. 模型不能自报可信 Verification、handlingStatus、Decision selectionTrace 或内部 hash。
3. 观测证据句柄必须真实存在、属于当前 Query Task；观测现象不自动证明业务意图。
4. Spec 修订使用当前不透明 revision，原子提交；过期修订不覆盖。
5. 结果候选必须绑定 Spec、查询身份及实际执行解释；探索 Artifact 不能直接升级发布。
6. 身份不匹配、安全或权限违规、证据充分的 Hard Constraint 违反仍阻断对应执行或交付。
7. 输出形状规则只有在题意、并列政策和适用条件明确时才拥有阻断权；不是把所有 Top-N 都机械解释为恰好 N 行。
8. material population 平局不能靠稳定排序、披露、预算耗尽或模型自述变成 handled。
9. 发布前以及 CSV 物理重执行前重新检查当前身份与政策；失败不生成成功 Receipt。
10. 允许带披露交付不等于 Approved 或 verified，也不是错误重试若干次后的自动放行。

## 4. 目标设计：拆开三个判断

| 判断 | 输入与职责 | 产物 |
|---|---|---|
| 语义状态 | Hypothesis、Verification、Decision 和 Evidence Authority | 可信状态、未决项、解释分歧 |
| 执行资格 | 当前 Spec、已具体化的执行解释、只读安全与资源约束 | 允许形成私有结果候选，或明确拒绝原因 |
| Delivery Policy | 候选身份、语义状态、Review Outcome、必要授权和环境政策 | 交付、带披露交付、需要确认或禁止交付 |

三个判断由 Runtime 统一协调，但不得用 `handlingStatus` 一个布尔值代替全部判断。

### 4.1 私有候选不等于发布

`query_database(mode=result)` 仍形成私有候选和 Internal Evidence，只有后续 publish/export 成功才是用户可见交付。

允许执行必须同时满足：

- 存在当前有效 Spec；
- 此次采用的业务解释已具体到能够写出查询；
- SQL、权限、安全和资源检查通过；
- 候选精确记录当前解释，不把未决项省略；
- 未发生已确认的 Hard Constraint 违反。

“口径尚未证实”可以执行；“口径尚未定义，连采用哪一种都不知道”不能执行。没有执行解释时返回 `interpretation_required`，不由 Runtime 猜测。

严格模式默认也允许满足条件的私有候选执行，严格性作用于交付。若特定产品要求澄清前禁止计算，应作为 Host 明确配置的执行限制，而不是复用 unhandled 通用阻断。

### 4.2 三种交付行为

以下为目标行为名称，不是现有配置字段；具体版本在实施时冻结。

| 环境政策 | 未决但可执行的候选 | 重大总体平局 | 交付要求 |
|---|---|---|---|
| 带披露交付 | 可交付，保留 unresolved/unhandled | 可交付一个明确登记的暂定解释，不自动选择 Decision | 预先启用该政策；解释、替代项、理由与限制绑定 Receipt；不标记 Approved |
| 交互确认 | 重大未决项先请求用户确认；普通未决项按预设披露规则处理 | 必须确认后交付 | 无确认能力时返回 clarification unavailable，不静默切换政策 |
| 严格交付 | 未满足可信处置条件时不交付 | 不交付 | provisional 或披露不能替代所需证据/确认 |

“重大”由 Runtime 根据已有受约束的结构化证据与总体检测规则判断，不在新模型协议要求填写 materiality 或自由风险评分。能确定的标记已知影响，不能确定的保留 unknown；“未检测出重大影响”不等于 non-material。交互政策对未知影响先澄清，严格政策不将其作为已处置放行；带披露政策必须连同影响范围未知一起披露。不得仅因问题尚未展开为 Decision 就跳过检查，零选项问题也在政策检查范围内。

已经确认的约束违反或已知 Semantic Disagreement 不走普通未决快捷路径，继续服从既有明确政策及必要的 Publication Authorization。政策未配置时不因本次升级自动放宽生产行为。

## 5. 模型协议减负

### 5.1 仅保留一个计数事实来源

新模型协议删除 `assumptionVector` 输入。选项可附带 `assumptionProfile` 作为补充信息，不再将五维分类作为登记问题或形成暂定执行解释的必填表单：

```text
选项附带的 assumptionProfile（若有）
→ Runtime 规范化稳定 ID
→ Runtime 派生 assumptionVector
→ Runtime 内部选择与审计
```

提交 profile 时保留非法值检查、去重要求、五维结构和 null 语义；缺省表示该清单未知，不代表没有附加假设。缺省时内部各维保留 unknown/null，不补零，也不把未知清单用于证明某选项假设更少。Runtime 不为了满足 effect 要求凭空创建假设 atom。

最小附加假设选择若因资料不足无法区分，应正常保持未决，并由第 4 节政策处理；不要求模型先补齐 profile 才能登记或执行暂定解释。

旧协议通过版本化 Adapter 读取和校验 vector；新模型 schema 不暴露它。内部结果仍可保留派生 vector，避免无必要地重写 selector 和历史审计格式。

### 5.2 单一不确定性写入协议，双轨内部实现

**模型只登记不确定问题及其选项；Runtime 自动展开 Hypothesis、Ambiguity、Decision、Interpretation 和关联。模型不需要判断“该写假设还是建决策”。**

新版本 `update_answer_spec` 保留七槽位与当前不透明 `baseRevisionId`，用 `uncertainties` 替换模型侧 `hypotheses`、`hypothesisBindings`、`decisionProposals` 写入入口。`legacyHypothesisRefs`、内部对象 ID 和可信选择结果不进入新模型写入 Schema。

下面只展示 envelope 中的不确定性片段，不是完整工具调用：

```json
{
  "uncertainties": [
    {
      "paths": ["/metric"],
      "question": "跨年度平均应采用哪些产品月份？",
      "options": [
        {
          "key": "intersection",
          "statement": "仅纳入两个年度都存在的产品月份"
        },
        {
          "key": "union",
          "statement": "纳入任一年度存在的产品月份"
        }
      ],
      "proposedExecutionOption": "intersection",
      "reason": "当前暂按可配对月份计算，尚无业务定义支持",
      "evidenceRefs": []
    }
  ]
}
```

模型的核心输入只有问题、槽位、已知选项、依据，以及可选的暂定执行提议。`proposedExecutionOption` 引用本问题中的 option key；有该提议时必须解释 reason。选项也可附独立的 reason、evidenceRefs 和第 5.1/5.3 节的结构化补充信息；这些均不构成第二种对象入口。

`options` 显式允许零个、一个或多个选项，不设最少两个的门槛：

| 输入情况 | Runtime 展开行为 |
|---|---|
| 零选项 | 保存 Ambiguity 与问题引用；影响相关执行时返回 interpretation_required，不编造 Hypothesis 或选项 |
| 一个未证实选项 | 建立相应 Hypothesis 与路径绑定，不要求创建 Decision |
| 两个及以上不同选项 | 建立候选 Hypothesis 与关联 Decision；无须先判定 material 才建选择关系 |
| 提议执行一个已有选项 | 形成暂定执行 Interpretation；不写可信 Decision selection，不改变 handlingStatus |
| 获得合格证据或用户确认 | 通过原有可信流程更新对应内部对象，而非接受模型自报已确认 |

“不同选项”只做结构性重复规范化：完全重复的选项合并并返回 key 映射，不把自由文本语义相似度当作合并证据。无法判断是否实质不同可以保留待澄清，不由 Runtime 补造竞争解释。

本例只说明“交集/并集”的选择登记，不表示均值计算口径已经完整。缺席、NULL、零分母和聚合顺序若仍影响答案，必须在七槽位或其他 uncertainty 中具体化后才能执行。

### 5.3 自动建立关联，不自动裁定业务语义

内部对象构建和业务影响识别是两个步骤：前者确定性自动化，后者仅在证据覆盖范围内判断。

- 新模型不必填写 `affectedAspects`、materiality 或内部 Decision 类型；Runtime 从 paths 和可选结构化声明派生已知影响。
- 已有规则确定 `/entity`、`/filters` 涉及 population 时，自动登记影响范围。
- `/metric` 的隐式总体变化不能靠字段名可靠推导时，保留 unknown；必要时询问具体业务影响，而不是询问“是否应该创建 material Decision”。
- 派生 population 仅表示需要检查总体影响，不证明实际是 restrict，也不证明这种限制正确。
- 未检测到 population 不证明 non-material；政策必须处理 unknown，不能通过少建内部对象或漏填声明规避澄清。

`populationEffect` 可作为选项的结构化补充，但必须相对于已登记的资格总体解释。若参照总体不清楚，应保持未知；不得因为向量全零就声称 preserve。

本阶段不新增自然语言分类 Agent 或 SQL 语义证明器，不自动发明资格总体。自动展开不是自动选择；material population 平局保护继续有效。

### 5.4 身份、修订与兼容

- Runtime 返回 task-scoped 不透明 `uncertaintyId`；后续模型在同一入口引用该 ID 更新问题，无须携带 H/DEC/ALT ID。
- options 的 key 是模型可读的局部引用，不是候选或可信身份；Runtime 将其映射到版本化内部对象。
- 零、一、多选项之间变化只调整同一问题的内部展开关系，不要求模型执行“升级/降级 Decision”。
- 同 revision 的相同输入重试不重复建对象。选项内容改变时新建对应语义版本，旧证据资格、授权和候选不能仅凭 key 相同迁移。
- 当前 uncertainty 及其展开对象在一次 Spec 修订中原子保存；七槽位、路径、执行提议和内部引用一起校验。拟议执行选项与 facet 描述明显冲突时要求修订，不静默改写槽位。
- Runtime 派生与 uncertainty 相关的 facet 状态、hypothesisBindings 和兼容映射；模型不重复填写同一事实。
- 删除问题、减少选项或改写 ID 不是解决歧义的证据。语义上仍相关的未决项不能因省略而消失；范围撤销须走可审计的 Spec Authority 变更并使相关候选失效。
- 新模型 Schema 只接受统一入口，拒绝混合旧字段，不同时提供三种可选写法。旧字段仅由冻结的旧版本 Adapter 接受。

`uncertainties` 及其内部映射属于同一 Answer Spec 版本链，不另建独立审批或可信状态存储。

### 5.5 回执、读取和提醒也统一到问题

仅修改输入 Schema 不足以消除双轨负担。新模型的更新回执、计划读取、错误和提醒均围绕 `uncertaintyId` 与 option key 展示，不再要求模型处理 H/DEC/ALT 关联。

示例回执含义：

```text
U1：尚未获得确认
当前暂定执行：intersection
影响范围：population
内部候选：允许执行
交付：需要用户确认
下一步：请确认采用交集还是并集
```

状态与下一步均由 Runtime/Delivery Policy 产生。完整 Hypothesis/Decision 映射继续保留在内部审计和 Host 调试视图；默认模型工具不回显要求操作的双轨表单。对未知影响、无选项问题或确认不可用，返回其真实状态而不是上述示例中的固定动作。

### 5.6 结构错误与业务未决分别处理

- 非法路径、未知 uncertainty/option 引用、伪造 Evidence、过期 revision、重复非法 ID：拒绝提交，原状态不变。
- 零选项、合法 unknown、证据不足、候选平局：正常保存为未决，不视为工具参数错误。
- effect 与假设清单矛盾：返回 uncertainty/option 下的具体字段路径；允许调用方通过新修订如实改成 unknown，不自动改计数使其过关。

不得在一次失败修订后，默默用此前旧口径执行用户以为已修改的查询。

## 6. 关键区分：执行 Interpretation 不等于选定 Decision

这是取消前置死锁但保留总体保护的核心。

### 6.1 执行解释的最小记录

优先复用项目已有 Interpretation 与候选绑定机制，避免新建一套平行状态机。实施时确认现有结构是否满足以下字段；不足时仅补字段：

| 内容 | 来源 |
|---|---|
| 涉及的不确定问题与 facet | 当前 Spec 的 uncertaintyId；内部 Hypothesis/Decision 引用由 Runtime 映射 |
| 本次执行的解释 | Solver 通过 proposedExecutionOption 明确提出，不能由 Runtime 稳定排序猜选 |
| 被保留的竞争解释 | 已登记的真实 alternatives |
| 采用理由与证据引用 | 区分题面字面依据、权威证据和模型暂定判断 |
| 状态 | 暂定执行，不产生可信处置状态 |
| 身份 | Runtime 绑定当前 revision 和候选 |

具体执行解释属于版本化 Answer Spec 内容：若改变语义，先修订，再执行。现有 facets 已明确表达且只有单个已登记解释时，Runtime 可直接形成其快照；不得要求模型重复抄写。

存在多个竞争解释时，模型在原 uncertainty 中明确当前执行哪一个，无须另填 Interpretation 或 Decision 表单。新引用的结构与范围由 Runtime 校验；SQL 与 Interpretation 的语义一致性按既有 Query Digest/Review Coverage 检查，覆盖不足须披露，不能声称已证明一致。

### 6.2 material population 平局示例

```text
模型视图 U1：跨期平均采用交集还是并集，证据不足
Runtime 内部：关联 Hypothesis 未决，Decision pending_clarification，无 selectedAlternativeId

Solver 在 U1 提议本次暂定执行“交集”，同时保留“并集”解释和未决原因
→ Runtime 原子展开为新 Spec revision
→ result candidate 绑定 U1 的“交集”解释及内部引用
→ 关联 Hypothesis 仍 unresolved/unhandled

带披露政策：可按授权的环境政策发布暂定结果
交互政策：询问用户，未确认不发布
严格政策：未满足可信处置要求，不发布
```

不能将该流程实现为“强行选择交集，然后标记 provisional_selected/handled”。若 Solver 也没有理由提出一个具体解释，返回无法确定，而不是按 alternative ID 排序挑选。

用户后续确认改变总体时，重新修订并生成新候选，不给旧候选换标签后发布。

## 7. 统一政策实现与交付绑定

### 7.1 一个政策 Module，多处防御性调用

在现有 Query Assurance/Delivery Policy 所在 Seam 内收敛实现，不增加独立审批服务。内部统一判断返回：

```text
执行：allowed | interpretation_required | blocked
交付：allowed | allowed_with_disclosure | needs_confirmation | blocked
附带：reason codes、所需披露、可执行下一步
```

以上是拟议内部返回值，不是模型可写的状态。

所有入口使用同一份判断：

- `agent-assembly.ts` 工具入口；
- `query-assurance.ts` 的 recordPreview、convergeCandidate、publishCandidate；
- inline publish；
- CSV stream 重执行之前；
- 持久化恢复与幂等发布路径。

将 `assertNoUnhandledHypotheses()` 和 `assertResultDecisionExecutable()` 中混合的语义处置、执行和发布限制拆分后纳入该实现。不能仅删除其中一个调用，留下另一条平局阻断形成假修复。

### 7.2 Artifact、Disclosure 与 Receipt

沿用现有记录，补齐以下身份和披露信息：

- 当前 Spec revision 及候选身份；
- uncertainty/option 版本映射、执行 Interpretation 与未决问题及 Hypothesis 快照（包括未展开为 Hypothesis 的零选项问题）；
- 已选 Decision 与仍未决 Decision，二者分开；
- 生效的执行/Delivery Policy 版本；
- 实际 Review Outcome、Coverage 和语义分歧；
- 必要的 Publication Authorization；
- 交付状态与披露内容。

普通未决放行不修改 hypothesis disposition。inline 和 CSV 均需可访问的 Disclosure；CSV 不通过额外数据行破坏用户要求的表结构，披露放在发布消息或伴随元数据中。

发布复查应关注当前 revision、解释身份、政策和授权是否仍有效，不能退回“当前仍有 unhandled 一律拒绝”。政策变化使旧候选失去授权时明确拒绝或要求重新授权，不能复用旧 Receipt 绕过。

## 8. 可行动报错与有界处置

### 8.1 返回具体问题，不教模型造数

复用现有 decisionActions 的内部 issue 来源，将其映射成模型侧统一 uncertainty action，而不是另建纠错 Agent。

模型回执建议字段：`code`、`uncertaintyId`、`optionKey`（若适用）、`paths`、`observed`、`constraint`、`allowedActions`。`decisionId`、`alternativeId` 和内部栈只保留在审计/Host 调试记录中，不要求模型自行反查映射。

示例含义：

```text
问题：声明 populationEffect=restrict，但没有记录对应额外排除假设。
动作：补充真实存在的假设及其依据；或承认目前无法确定 effect；或澄清。
```

禁止建议“把 unsupportedPopulationExclusions 改成 1”。Runtime 的任务是指出矛盾，不是供应业务事实。

### 8.2 重试预算与语义修复预算分开

- 机械冗余通过派生消除，不消耗模型重试。
- 对同一未变化的具体业务矛盾，默认只允许一次针对性修订机会。
- 无新证据且修订仍无效时，转向合法 unknown/澄清/政策允许的暂定解释或明确结束，不继续同义改写。
- 这不覆盖现有“结果 SQL 与 Spec 差异最多一次自动语义修复”的独立限制。
- 不通过拒绝所有后续 Spec 更新来实现次数限制；真实新证据、用户澄清仍能形成新修订。

去重结合问题标识、相关证据与动作进度；仅修改 ID、排序或无关槽位不重置重试额度。

### 8.3 提醒只说当前还能做的事

复用现有 usage ledger 和工具能力信息生成行动建议：

| 当前情况 | 下一步 |
|---|---|
| 有未决点且仍有针对性探索预算 | 指向一个可能改变答案的具体证据缺口 |
| SQL 探索耗尽但存在明确未读的相关文档 | 指向该文档，不声称所有证据渠道都已关闭 |
| 无可取得的新证据，有澄清工具 | 提交具体选择题给用户 |
| 无澄清工具，带披露政策已启用 | 登记可执行暂定解释，执行并披露；无法具体化则结束 |
| 无澄清工具，交互或严格政策 | 明确返回需要确认/无法确认，不继续搜索猜测 |

提醒与政策读取同一份任务状态；保留当前最多三次提醒的上限作为兜底，不增加上限。不因预算耗尽建议扫描磁盘，也不为了尽快结束绕过剩余执行资源限制。

本节只处理查询/交互行动预算，不涉及上下文管理或生成截断恢复。

## 9. 实施阶段与完成标准

### Phase 0：冻结行为与最小回放

工作：

1. 固定当前工作树快照和协议版本；仓库已有大量未提交修改，不混入或覆盖其他工作。
2. 从 local017 提取最小脱敏协议事件序列，不需要再次消耗完整模型运行来验证机械错误路径。
3. 构造 profile/vector 冗余、双轨对象选择、零/一/多选项转换、未知影响、总体平局、探索预算耗尽 fixture。
4. 固定现有严格模式行为和候选身份负例。

完成标准：有可单命令运行的确定性回放，能捕捉目标失败；取得并记录修复前输出。完整线上重现不是本阶段必要条件。

### Phase 1：协议减负，不改变交付政策

工作：用 uncertainties 替换双轨写入入口；实现确定性内部展开和问题级读写投影；删除新模型协议 vector、隐藏 legacy 引用、派生可确定 aspects、透出问题级 issue，保留旧协议 Adapter。为零选项与未知影响保留待澄清状态，缺 profile 不补零。

完成标准：模型无需选择对象类型或填写内部引用；零/一/多选项均可登记，读写回执不把双轨表单重新暴露；旧协议回归通过；可信状态、证据引用与非法输入测试仍通过；未启用新 Delivery Policy 时，不因接口替换降低旧严格交付要求。

### Phase 2：执行与交付解耦

工作：落实后继 ADR；统一政策 Module；补齐执行 Interpretation 绑定；同步所有 result、publish、stream 与恢复入口。

完成标准：普通未决可形成私有候选；material tie 不转 handled；三种政策按矩阵运行；身份负例仍在物理执行/发布之前失败。

### Phase 3：有界处置与协议文档同步

工作：行动感知提醒、同问题去重、一次针对性修订后分流；更新提示词、领域文档、工具 schema、配置和协议版本。

完成标准：预算耗尽不再给不可执行建议；换 revision 或改 ID 不能制造重复循环；无确认能力时终态原因明确；不存在代码放行而提示词仍要求全部 handled 的矛盾。

### Phase 4：工程验收与灰度

工作：先定向/全量回归及独立复审，再经单独授权运行同配置固定题集对照。

完成标准：满足第 10、11 节。未运行 A/B 时仅标记工程验收，不报告正确率收益。

## 11. 灰度评估与停止条件

### 11.1 运行纪律

- 本方案不授权启动评测；实施完成后单独确认预算和运行计划。
- Control 与 Treatment 必须来自可复现快照，固定题单、模型、数据、工具预算、并发和 evaluator。
- 新方案含政策变化，不能拿旧 reminder-only A/B 或旧版 Control 直接充当同配置基线。
- Manifest 记录协议/schema/prompt、规范化/选择/默认政策及 Delivery Policy 的生效版本。
- 使用完整配对结果，不逐题择优重跑拼接。固定 10 题只作 smoke，不声称可泛化；扩大上线前另做预先冻结的独立留出集。

### 11.2 指标

必须分别报告：

- 官方正确率：固定题集分母，以及交付条件下的正确率；
- SQL、CSV/inline、Publication Receipt，三者不混为一个指标；
- 非交付原因：澄清、政策拒绝、身份失败、预算/提供方失败等；
- unresolved 交付率及其 Disclosure/Interpretation binding coverage；
- 错误可信升级、重大总体 stable-order 选择、身份绕过次数；
- 每题元数据纠错轮次、提醒次数、Turns、Tool Calls、Token 与时延；
- 新协议是否出现让模型选择 Hypothesis/Decision 类型、补内部映射或凑两个选项的交互，以及零/一/多选项生命周期完成情况。

交付率增加不能单独宣告成功；handled 比例下降也不自动表示退步，因为本方案允许真实未决保留。

### 11.3 硬验收与停止条件

硬验收：

1. 既有身份、安全和可信状态约束的工程测试全部通过。
2. material tie 被稳定排序或执行 Interpretation 错误升级为 handled 的次数为 0。
3. 所有带未决成功交付样本的解释与披露绑定覆盖率为 100%。
4. 同一无变化业务矛盾最多一次针对性修订，随后确定分流。
5. 新模型 Schema 不接受双轨写入，模型可仅用 uncertaintyId/option key 完成登记、修订、执行提议及澄清；无要求选择内部对象类型的交互。
6. 零选项和未知影响不遗漏政策检查，缺 profile 不被当成零假设优势。
7. 独立复审未留下未解决的高严重性问题。

灰度停止条件：出现身份绕过、未授权交付、虚假验证或披露丢失，立即停止新政策推广；若成本增加却未减少协议往返或政策性非交付，不继续加功能，先回查设计。

正确率非劣效界限、成本阈值和统计判断在评测前另行登记；10 题 smoke 不足以证明非劣效，不在本方案虚构统计显著性。

## 12. 兼容、回滚与残余风险

### 12.1 兼容与回滚

- 版本化新模型 schema、规范化规则和 Delivery Policy；任务开始时冻结，禁止同一任务中无记录切换。
- 旧 Artifact/Receipt 不改写，旧 hypothesis disposition 不因升级重新“洗白”。
- 按冻结的显式协议版本路由：旧版本由旧 Adapter 解释，新版本必须符合 uncertainties Schema；不得仅因字段缺失自动降级旧协议。无法安全解释的记录明确不可用，不通过猜测补字段恢复发布。
- 保留旧政策实现供旧任务和对照运行使用；新政策灰度按新任务启用。
- 回滚让新任务回到旧配置，已发布事实不撤写；已有任务按冻结版本处理或明确终止迁移。
- 避免 schema × Hook × 多个分散布尔开关形成组合爆炸；采用少量冻结、可测试的环境 Profile。

### 12.2 残余风险

1. 模型仍可能提出错误总体、漏报不确定问题或漏列选项；单入口、自动展开和向量派生均不能解决业务意图缺失或证明选项穷尽。
2. 允许带披露交付可能增加错误答案的可见数量，必须同时观察正确率和产品可接受性。
3. 已登记 Interpretation 与实际 SQL 的匹配仍受现有检测覆盖限制，绑定身份不等于语义证明。
4. 交互/严格模式下，无法取得用户确认仍可能不交付；目标是可解释终止，而不是保证每题有结果。
5. 本方案不处理上下文膨胀、生成截断和空响应终态；因此即使完全实施，也不能声称 local017 的所有故障路径都已修复。
