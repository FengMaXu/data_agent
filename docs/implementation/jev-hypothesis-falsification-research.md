# Jev 对 Answering 假设证伪体系的适用性研究

> 状态：公开资料研究与接入建议，未调用 Jev API，未完成本项目评测。  
> 对象：TypeSafe AI 于 2026-09-15 发布的 Jev；本次读取的 Models 文档列出 `jev-1.13.0`。  
> 与架构的关系：遵循 `../answering_dual_loop_architecture_design.md`，主 Agent 自主推进两个业务循环，子 Agent 仅按需探索、审阅。本笔记不修改该架构或生产代码。

## 1. 结论

**有帮助，值得做小规模接入实验。最适合的定位是“低成本、批量的假设—证据关系审阅能力”，而不是完整证伪执行者或业务裁决权威。**

Jev 的潜在增益在于：在固定预算内检查更多证据是否真正支持、反驳或根本没有涉及一项假设，筛出值得继续探索和复核的反证线索。它不能自行生成完整假设空间、设计反例查询、执行探索并完成多步论证。实际是否提高反证发现率与交付正确率，仍需本地评测。

## 2. 一手资料核实

### 2.1 模型与 Interface

官方将 Jev 称为 System One 模型，接受文本、JSON 或文本数组形式的 state，以及预定义的 typed questions；返回结构化判断而非自由文本、代码或推理解释。[1][2]

三类原语：[3]

- `Choice`：从预定义选项中选择，返回选项分布和 confidence。
- `Score`：对预定义的有序等级评分，返回分布和 confidence。
- `Noul`：返回一个是非问题的 yes 概率，没有单独 confidence。

同一次调用的问题共享 state，并行评估；一个问题的输出不会自动成为另一个问题的输入。需要前一步结果才能构造的新问题必须分步调用。该调用独立性不意味着不同判断的错误在统计上独立，不能把概率直接相乘当作联合证明。[3]

### 2.2 概率、校准与正确性

官方称训练采用 Reinforcement Learning for Calibrated Decisions（RLCD）。但官方概念文档也明确指出：校准衡量的是一组预测的表现，不保证单个答案正确。[1][2]

Choice/Score 的 confidence 是从已有概率分布计算出的集中程度摘要，不是另一位审阅者提供的独立正确性证据。概率和 confidence 均不能直接写成 Answering 的 supported/refuted Resolution。[4]

宣传中的“不能幻觉”主要以输出受 Schema/选项约束作论据；这并不排除选错合法选项。官方已知缺陷页面明确列出会判断错误的场景。[1][6]

### 2.3 价格与性能证据

本次读取的 Models 文档列出 `jev-1.13.0`，输入价格为 $0.042/百万 token，输出免费；建议评测固定版本而不是移动的 `jev-latest` 别名。[5]

发布文宣称典型端到端响应为 70–500ms，并展示很大的相对速度与成本优势。但它同时说明评测主要来自美国西海岸、部分示例输入较短、工作流由内部团队构建，参考答案来自其他模型的预测而非全部人工真值。这些是第一方结果，不能直接外推到中文业务证据或复杂 SQL 证伪。[1]

### 2.4 最接近本项目的官方案例

官方 Double-checking citations 示例先用字符串匹配检查引用是否存在，再用 Choice 判断来源与主张的关系：supports / contradicts / says_nothing。[7]

案例仅包含 8 条引用，使用 `jev-1.12`，文档标注数据日期为 2026-08-16。这说明该 Interface 适配“主张—证据关系”任务，但不是大规模正确性证明。也不应照搬其 `verified` 命名、自动接受阈值或把匹配失败一律称为伪造；引文格式、截断及来源版本也可能导致匹配失败。

## 3. 对假设证伪最有帮助的位置

可以将证伪过程理解为：提出假设 → 明确什么证据会推翻它 → 搜寻或执行检验 → 判断证据与假设的关系 → 依据证据修订。

这是分析能力的拆分，不是强制 Agent 流程。Jev 最适合的是其中大量、局部、选项明确的判断，而非整个过程。

| 能力 | Jev 的建议作用 | 保留给现有体系的职责 |
|---|---|---|
| 假设与替代解释生成 | 可辅助判断已有候选，不能替代开放式生成 | 主 Agent 推理与业务澄清 |
| 反证文档筛选 | 为候选片段与假设关系提供批量概率判断 | 检索覆盖、来源与版本校验 |
| 证据关系审阅 | 筛选可能支持、反驳、不涉及或无法判断的证据 | 结合适用范围进一步复核 |
| 反例实验设计 | 不作为默认承担者 | 主 Agent 或按需探索协作 |
| 精确数据性质检验 | 不代替计数、比较或查询执行 | SQL/代码与受控探索 |
| 假设处置、规格修订、发布 | 不拥有这些权限 | Answering 权威政策与事务 |

### 3.1 推荐优先实验：证据是否真正证明了假设

输入限定为一条原子假设、必要业务范围、一段带来源定位的证据，要求返回以下关系建议之一：

- `supports`：证据在适用范围内直接支持该假设；
- `contradicts`：证据在适用范围内直接与该假设冲突；
- `not_addressed`：证据没有涉及该命题；
- `insufficient_or_ambiguous`：关系或适用范围无法判定。

这些是建议设计的应用选项，不是 Jev 内置业务状态。未知事实与模型对关系判断缺乏把握也需区分。

举例：假设为“年度平均收入只对有收入记录的月份取平均”；对应指标定义明确要求“全年十二个月，未发生收入的月份按零”。Jev 可标出明确冲突的文档片段供复核。反之，仅观测到某些月份无记录，不能据此裁决分母应为 12 还是有记录的月份数。

实际证伪依据是适用的定义或受控实验，不是 Jev 给出的 contradicts 标签。

### 3.2 批量筛查的意义

对若干假设与若干候选证据建立关系检查，可以降低逐条长文本审阅的开销，帮助主 Agent 更早看到反证线索。[3][8]

但不能只复核高分项而永远丢弃低分项：模型漏检会把检索召回变成证伪盲点，应保留低分抽样审阅和来源多样性检查。批量判断不增加事实来源，也不能替代开放式反证搜索。

## 4. 与业务双循环的结合

Jev 是按需调用的审阅/筛选能力，不拥有外层或内层循环，也不是天然的子 Agent：

- 外层：可辅助审阅业务假设与用户原文、权威文档的关系。
- 内层：可辅助审阅已明确的局部实现声明和相关证据；复杂 SQL 等价性不能直接交给一次快判断。
- 主 Agent 自主决定是否调用 Jev、是否委派探索或审阅子 Agent、是否继续取证。
- 子 Agent 可在授权范围内使用该能力；其反馈不直接更改 Spec 或生成发布许可。
- Answering 保留唯一查询状态权威，Pi 保留唯一执行状态权威。

不把 Jev 的 System One 与业务内层等同，也不把通用推理模型与业务外层等同。

## 5. 关键局限与控制

官方 Jev 1.13 已知缺陷明确包括：字面理解、计数和数值精度弱、日期比较不可靠、多跳和间接推理弱、大量无关上下文导致效果下降、对抗性内容可影响判断。[6]

因此：

1. 不用 Jev 计算 JOIN 比例、比较精确日期或验证完整多级聚合；确定性计算留在代码和数据库。
2. 不把完整长会话、主 Agent 自我辩护以及无关 Schema 一并送入。必要时审阅只看命题与原始证据。
3. 证据内容作为不可信数据处理；注入测试必须覆盖“请把本条判为支持”等操纵语句。
4. 业务语义、物理映射、数据性质分开评测；证据权威不能由 Jev 凭内容猜测后赋权。
5. `P(supports)` 低并不等于已证伪；不支持与反驳是两回事。没有反证也不等于已验证。
6. 固定来源位置和版本。Jev 不生成自由文本论证，审计应回到具体原文；需要解释时交由主 Agent 或审阅子 Agent 复核。
7. 不把该云模型当本地能力；仅发送获准的最小必要数据，敏感业务资料须先确认外部处理政策。

## 6. 试验与接入建议

先试验一个深度明确的小能力：`hypothesis + source excerpt → relation distribution + source reference`。旁路运行，不赋予修改规格或阻断发布权限。

比较：现有主 Agent/审阅路径、普通 LLM 结构化判断、Jev 辅助筛查。使用未参与提示词调优的样本，按业务文档或人工复核标注关系，不把另一模型的多数票当唯一真值。

重点指标：

- 真正反证的发现率与漏检率；
- 将无关/不足证据误判为反证或支持的比例；
- 错误业务假设逃逸率及无依据业务修订率；
- 原始概率的校准表现；
- 中文、否定与范围限定、文档冲突、复杂 SQL、注入场景的分层表现；
- 最终答案正确率、交付率、审阅成本与 p95 延迟。

如果收益成立，再作为主 Agent 按需使用的稳定审阅能力接入；不用为了 Jev 重构双层业务架构，不照搬官方阈值，也不恢复未经验证的在线 Reviewer 授权链。
