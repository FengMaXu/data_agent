# Choice 以探针输出为准，并纳入处置完整性阻断

本 ADR 修订 ADR-0003 第 3 条的硬阻断范围，并补充 ADR-0004 的 Spec 状态转移规则。

## 背景

Spider2 错题分析（2026-09-26）显示，选择类错误并不主要来自"不知道哪个候选对"：

- 运行时不知道一个 Choice 的各候选会不会产生不同的输出，Agent 的探索和裁决精力大量花在不改变结果的歧义上。
- `compare_hypotheses` 接收自由文本候选，运行时无法把建议对应到 Spec 中的 Choice；Agent 可以用无需理由的临时选择（provisional）越过建议的倾向（local028、local031）。
- Choice 的处置结果与结果 SQL 之间没有任何关联；Spec 记录了一个口径，交付的结果却按另一个口径计算，运行时无法察觉。
- 决定结果的计算细节（计数粒度、时间字段、分母等）经常没有被列为候选；运行时看不到这种遗漏。

## 决策

1. **探针（Choice Probe）。** Choice 的每个候选可以绑定一次 exploration 执行，运行时按输出比对规则计算其结果指纹。所有候选指纹相同的 Choice 可以处置为 `equivalent`：由 Agent 提交、运行时核验指纹后接受，不需要理由、建议和披露；视图中标明每个 Choice 的输出是相同、不同还是未知。选定或临时选择一个 Choice 之前，每个候选都必须有探针或声明不可探测的理由。
2. **建议绑定 Choice。** `compare_hypotheses` 只比较一个 Choice 的全部候选。运行时把建议记入受信任的 Advisory Ledger；建议本身仍不是证据，也不能单独处置 Choice。
3. **处置须说明理由，偏离建议须说明依据。** 临时选择与选定一样需要理由。当 Advisory Ledger 对该 Choice 记录了明显倾向而处置结果不是该倾向时，处置必须附带偏离理由和至少一条已准入证据。
4. **处置须在结果中兑现。** 结果查询的指纹若等于某个未被采纳候选的探针指纹、且不等于被采纳候选的指纹，该结果不能成为 Result Candidate。
5. **决策点必须显式声明。** Revision 必须对固定的一组决策点逐项声明"题面已规定（附经核验的题面引文）""不适用""由某 Choice 决定"或"由某 Hypothesis 假定"。仍有未声明的决策点时，Revision 不能进入 Ready，result SQL 与发布被阻断；exploration 不受影响。

## 与 ADR-0003 的关系

ADR-0003 的三类硬阻断保持不变，新增两类，二者都属于"处置生命周期完整性"，不判断哪个口径正确：

- 结果兑现了当前 Revision 未采纳的候选（决策 4）。判断依据是两次确定性执行的指纹是否相等，而不是业务语义。
- 存在未声明的决策点时的 result SQL 与发布（决策 5）。它与"存在 unhandled 假设时阻断"同类：只要求声明，不裁决声明内容。

指纹不可用（探针结果被截断、执行失败、候选声明不可探测）时，按 ADR-0003 记录为 `unavailable` 并披露，不阻断。

## 后果

- 每个 Choice 至少多出与候选数相等的探针查询；不影响输出的 Choice 不再需要裁决和建议调用，可部分抵消成本。
- 在创建 Choice 时直接选定（inline selection）只在全部候选声明不可探测时允许。
- 指纹比对只能发现"结果等于另一个候选"，不能证明"结果等于被采纳候选"；其他 Choice 的处置变化会让旧探针过时，此时兑现检查只能给出 `unavailable`。
- 决策点清单是固定、有限的类目，不覆盖所有可能的歧义；它让遗漏可见，但不保证 Agent 声明正确。
